# ESP32OLED CI/CD Implementation Plan

> **For Hermes:** Implement this plan task-by-task after explicit execution approval. Do not modify `/home/jlsernav/hardware/esp32ToneHub`.

**Goal:** Build `esp32oledCI` as a local deployment client that downloads a compatible ESP32-C3 firmware package from `jorgelserve/espCICD` or a configured GitHub firmware repository, verifies it, and deploys it over USB first and OTA later.

**Architecture:** `esp32oledCI` is a Python CLI and package verifier, not the firmware source. It consumes versioned firmware releases. The firmware itself must expose the required runtime capabilities—multiple persisted Wi-Fi profiles, automatic connection, BLE provisioning, fallback SoftAP, and eventually signed OTA. The CI/CD client must reject releases that do not declare the required board, partition scheme, protocol, and capabilities in their manifest.

**Repositories and scope:**
- Implementation repository: `/home/jlsernav/hardware/esp32oledCI` → `git@github.com:jorgelserve/espCICD.git`.
- Firmware reference only: `/home/jlsernav/hardware/esp32ToneHub` and remote `jorgelserve/esp32oled`. Never modify the local example during this plan.
- The firmware repository currently has no GitHub Release assets, so the first implementation must support a clear `no release` error and must not silently download source archives as firmware.

**Tech Stack:** Python 3.11, `uv`, `typer` or `argparse`, `httpx`/standard-library HTTPS, `pyserial`, `esptool`, pytest, GitHub Actions, PlatformIO release metadata.

---

## Non-negotiable requirements

1. Never modify `esp32ToneHub`.
2. Never flash a firmware file without validating its manifest and SHA-256.
3. Never treat a GitHub source archive as a firmware package.
4. Reject packages for another board or chip.
5. USB flashing is the first deployment path and recovery path.
6. OTA is a later phase and requires an OTA-capable firmware release.
7. BLE provisioning and multiple Wi-Fi profiles are firmware capabilities; the client only verifies and deploys them.
8. Credentials, tokens, Wi-Fi passwords, and PoP values must never be logged by the client.
9. GitHub API failures, missing releases, missing assets, incompatible manifests, checksum failures, and serial failures must have distinct errors and exit codes.

## Target package contract

Each published firmware release must contain a manifest such as:

```json
{
  "schema": 1,
  "project": "esp32oled",
  "version": "1.1.0",
  "channel": "stable",
  "board": "esp32-c3-devkitm-1",
  "chip": "esp32c3",
  "framework": "arduino",
  "partition_scheme": "ota",
  "firmware_asset": "esp32oled-esp32-c3-devkitm-1-1.1.0.bin",
  "firmware_sha256": "...",
  "firmware_size": 123456,
  "capabilities": {
    "wifi_profiles": 5,
    "ble_provisioning": true,
    "fallback_softap": true,
    "ota": false
  }
}
```

The initial USB package may also contain bootloader and partition binaries, but the client must distinguish a full factory image from an application-only OTA image. It must never flash an application-only image as a factory image.

- SHA-256 mismatch.

### Task 2.2: Wrap esptool safely

**Files:**
- Create: `src/esp32oled_ci/flasher.py`
- Test: `tests/test_flasher.py`

Implement a subprocess wrapper with:

- Explicit chip selection `esp32c3`.
- Timeout.
- Captured output with secrets redacted.
- Dry-run mode.
- Separate factory and application-only/OTA image flows.

The first factory flow should use a complete package containing bootloader, partitions, and application image. The application-only flow must require a compatible existing OTA partition layout.

### Task 2.3: Verify the device after flashing

**Files:**
- Create: `src/esp32oled_ci/device_verify.py`
- Test: `tests/test_device_verify.py`

Define a serial verification protocol that the firmware must expose, for example:

```text

CAP_BLE_PROVISIONING=1

```

The client must verify the expected version, board, and capabilities after reset. A successful `esptool` write alone is not a successful deployment.

## Adversarial acceptance matrix

The implementation is not complete unless these cases are tested:

| Case | Expected result |
|---|---|
| GitHub repository has no Releases | `NO_RELEASE`, no download, no flash |
| Release lacks manifest | `MANIFEST_INVALID`, no flash |
| Manifest targets ESP32-S3 | `BOARD_MISMATCH`, no flash |
| SHA-256 mismatch | `CHECKSUM_MISMATCH`, no flash |
| Existing verified package exists | Failed new download cannot overwrite it |
| Two serial devices are connected | Require explicit `--port` |
| Device disappears while flashing | Non-success result and recovery instructions |
| Serial reports wrong version | `VERIFY_FAILED` |
| Application-only image passed to factory flash | Reject before esptool |
| Firmware lacks BLE provisioning capability | Reject when capability is required |
| Firmware lacks at least five Wi-Fi profiles | Reject when profile requirement is five |
| OTA package has only SHA-256 and no signature | OTA remains unavailable |
| User requests source archive | Reject as non-firmware package |
| Credentials appear in subprocess output | Redact before display |
